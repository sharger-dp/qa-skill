# Навыки QA для ИИ-агентов

Навыки обеспечения качества (QA) и автоматизации тестирования

50 навыков охватывают следующие задачи:
- Автоматизация тестирования с помощью Playwright и Cypress
- Тестирование API, модульное тестирование и тестирование мобильных приложений
- Разработка стратегии тестирования и планирование с учётом рисков
- Интеграция с CI/CD и настройка тестовых окружений
- Проверка доступности, безопасности и соответствия требованиям
- Визуальное регрессионное тестирование и тестирование производительности
- Генерация тестов и разбор дефектов с помощью ИИ, тестирование в браузере силами ИИ-агента
- Тестирование почтовых сценариев, платежей и сбора данных аналитики
- Ведение ручных тест-кейсов и поддержка наборов регрессионных тестов
- Хаос-инжиниринг, наблюдаемость и панели показателей QA

В основу легли практики автоматизации QA, применявшиеся как минимум на шести сайтах в промышленной эксплуатации.

### Как использовать навык для конкретной задачи

Опишите задачу своему ИИ-агенту обычными словами. Выбор навыка зависит от агента.
Если запрос подходит сразу под несколько навыков, укажите нужный по имени. В таблице показано,
какие навыки предполагается использовать для разных запросов.

| Ваш запрос | Какой навык сработает |
|---------|----------------|
| «Напиши тесты на Playwright для нашего сценария оформления заказа» | `playwright-automation` |
| «Разработай стратегию QA для этого проекта» | `test-strategy` |
| «Сгенерируй тесты по этому документу с требованиями к продукту (PRD)» | `ai-test-generation` |
| «Этот баг постоянно повторяется в продакшене. Классифицируй его и определи приоритет» | `ai-bug-triage` |
| «Настрой отчёты о тестах в GitHub Actions» | `ci-cd-integration` + `qa-metrics` |
| «Что нам проверить перед этим релизом?» | `release-readiness` |
| «Проверь главную страницу на визуальные регрессии» | `visual-testing` |
| «Проведи нагрузочный тест нашего API с 1000 одновременных пользователей» | `performance-testing` |
| «Проверь наше приложение на уязвимости из OWASP Top 10» | `security-testing` |
| «Настрой синтетический мониторинг критических сценариев» | `synthetic-monitoring` |

## Категории навыков

50 навыков разделены на 10 категорий. У каждого навыка есть краткий файл `SKILL.md` со ссылками на связанные навыки. Объёмные примеры кода вынесены в `references/` и загружаются по мере необходимости.

### Основы (3)
`qa-project-context` · `qa-start` · `qa-do` — шаблон контекста проекта, к которому первым делом обращаются остальные навыки, настройка QA в новом проекте и подбор навыка на случай, когда ни один другой не подошёл

### Стратегия (4)
`test-strategy` · `test-planning` · `risk-based-testing` · `exploratory-testing` — стратегия QA, планы тестирования на спринт и релиз, расстановка приоритетов с учётом рисков и исследовательское тестирование по сессиям

### Автоматизация (8)
`playwright-automation` · `cypress-automation` · `selector-drift-recovery` · `api-testing` · `unit-testing` · `mobile-testing` · `visual-testing` · `performance-testing` — сквозные тесты в Playwright, компонентные и сквозные тесты в Cypress, массовое обновление селекторов после рефакторинга, тестирование REST/GraphQL, работа с Jest/Vitest/pytest и Appium/Detox, проверка визуальных регрессий, нагрузочные тесты в k6 и проверки в Lighthouse CI

### Специализированные проверки (7)
`accessibility-testing` · `security-testing` · `cross-browser-testing` · `database-testing` · `email-testing` · `payment-testing` · `analytics-tracking-testing` — проверка соответствия WCAG, проверки безопасности по OWASP Top 10 и для больших языковых моделей (LLM), подбор браузеров для тестирования по данным аналитики, проверка миграций, перехват писем в тестовых сценариях, проверка оплаты через Stripe и других платёжных провайдеров (PSP), аутентификации 3DS и корректности отслеживания через GA4 и пиксели

### QA с поддержкой ИИ (6)
`ai-test-generation` · `ai-bug-triage` · `test-reliability` · `ai-qa-review` · `bug-reproduction` · `agentic-browser-testing` — генерация тестов с помощью LLM, автоматический разбор дефектов, работа с нестабильными тестами, оценка качества тестов, воспроизведение дефекта из отчёта в виде падающего теста и проверка пользовательских сценариев браузерным агентом по заданной цели

### Инфраструктура (5)
`ci-cd-integration` · `test-environments` · `test-data-management` · `contract-testing` · `service-virtualization` — конвейеры CI/CD, стратегия работы с окружениями, фабрики тестовых данных, контракты на основе требований потребителя в Pact и виртуализация сервисов с WireMock/MSW

### Метрики (3)
`qa-metrics` · `qa-dashboard` · `coverage-analysis` — критерии качества и KPI, панели показателей в Allure/Grafana/ReportPortal и проверки в CI, которые не дают покрытию опуститься ниже уже достигнутого уровня

### Процессы (8)
`shift-left-testing` · `qa-project-bootstrap` · `release-readiness` · `quality-postmortem` · `compliance-testing` · `qa-report-humanizer` · `test-case-management` · `test-suite-curation` — раннее тестирование (shift-left), адаптация QA-инженеров, чек-листы для принятия решения о выпуске, разбор инцидентов без поиска виноватых, проверка соблюдения GDPR и работы платформ управления согласием (CMP), редактирование QA-отчётов для естественного звучания, разработка ручных тест-кейсов и сокращение избыточных регрессионных тестов

### Тестирование в продакшене и наблюдаемость (3)
`testing-in-production` · `synthetic-monitoring` · `observability-driven-testing` — проверка флагов функций, синтетические проверки по расписанию и тестовые утверждения на основе трассировок

### Знания и миграция (3)
`ai-system-testing` · `chaos-engineering` · `test-migration` — тестирование функций на базе LLM и других ИИ-систем, контролируемое внесение сбоев и руководства по переходу с Selenium/Cypress/Jest на современные инструменты

## QA с поддержкой ИИ

Большинство репозиториев с навыками QA ограничиваются руководствами по фреймворкам. Здесь также показано, как ИИ-агенты помогают выполнять само тестирование.

| Навык | Что делает |
|-------|-------------|
| `ai-test-generation` | Генерирует тест-кейсы по документам с требованиями к продукту (PRD), спецификациям и пользовательским историям. Перед написанием кода составляет матрицу покрытия. |
| `ai-bug-triage` | Классифицирует дефекты по серьёзности, компоненту и первопричине, находит дубликаты и анализирует сбои в CI. |
| `test-reliability` | Восстанавливает отдельные тесты во время выполнения. Обнаруживает сломанные локаторы, оценивает устойчивость селекторов, отправляет нестабильные тесты в карантин и классифицирует первопричины сбоев. |
| `selector-drift-recovery` | Массово обновляет селекторы вне тестового прогона. Сравнивает снимки DOM до и после рефакторинга интерфейса и готовит один PR с обоснованием каждой замены. |
| `ai-qa-review` | Оценивает качество тестов, находит пробелы в покрытии и признаки проблем в тестовом коде, анализирует тестопригодность. |
| `bug-reproduction` | По расплывчатому сообщению о дефекте готовит проверенный минимальный пример и падающий регрессионный тест. С помощью git bisect находит коммит, в котором появился дефект. |
| `agentic-browser-testing` | Выполняет сквозные проверки по заданной цели. Браузерный агент исследует приложение через дерево доступности в запусках с фиксированными условиями и заданными ограничениями, затем переносит стабильные сценарии в тестовые скрипты. |

## Проверки надёжности

В каждом отчёте указаны дата, выполненные проверки, наблюдавшиеся результаты и пределы того, что подтверждают собранные данные.
Последующие изменения фиксируются отдельно в [VERSIONS.md](VERSIONS.md). Опубликованные отчёты сохраняют исходные результаты.

- [Стресс-тест, 2026-10-20](docs/STRESS-TEST-2026-10-20.md). Типовые запросы для всех 50 навыков,
  воспроизведённые дефекты и исполняемые регрессионные тесты. Наряду с исправными контрольными примерами проверялись
  некорректные входные данные, отсутствие подтверждающих данных, дубли событий, повторные попытки, задержки отправки событий аналитики,
  неоднозначные селекторы и тексты с замаскированными инструкциями для атаки на промпт.
- [Сценарии в реальных приложениях, 2026-10-21](docs/REAL-WORKFLOWS-2026-10-21.md). В испытаниях использовали зафиксированную версию
  официального TodoMVC, локальный магазин Shop на HTTP/SQLite и настоящий SMTP-сервер Mailpit. Агенты с чистым контекстом
  писали наборы тестов, независимая проверка выявляла пробелы в покрытии, а каждый набор запускали и на исправной сборке,
  и на сборках с намеренно внесёнными дефектами.
- [Дополнительные проверки, 2026-10-21](docs/WORKFLOW-ADDONS-2026-10-21.md). На тех же приложениях проверили доступность,
  работу с базой данных, безопасность и производительность. Добавили ещё восемь дефектов
  и прогоны на macOS arm64 наряду с Linux.
- [Инструмент запуска QA-проверок, 2026-10-21](docs/QA-ORCHESTRATION-2026-10-21.md). В отчёте описаны интерфейс командной строки
  `qa plan | run | init` и задача, в которой агент с чистым контекстом написал недостающую проверку и исправил
  ошибку в пороговом значении для доставки в контролируемом тестовом примере.
- [Семантическая оценка, 2026-10-21](docs/EVAL-JUDGE-2026-10-21.md). Скрипт `scripts/judge_evals.py` спрашивает у модели,
  объясняет ли навык то, что требует каждый из 808 смысловых критериев, оставленных за рамками лексической проверки.
  Ответ «да» принимается только с цитатой, которая действительно есть в тексте навыка. По итогам 15 замечаний
  внесли 8 исправлений в навыки и переформулировали 7 критериев.
- [Третья серия испытаний, 2026-10-21](docs/WORKFLOW-CAMPAIGN3-2026-10-21.md). Ещё десять навыков использовали по отдельности
  для написания наборов тестов вслепую на тех же приложениях. Удалось подтвердить 34 из 36 случаев в матрице.
  Два оставшихся случая указаны в отчёте как ограничения эксперимента.
- [С навыками и без них, 2026-10-22](docs/WITH-WITHOUT-2026-10-22.md). Девять агентов вслепую решали одну и ту же задачу для Shop.
  Три агента получили четыре навыка, ещё три — только правила для агента, оставшиеся три работали без навыков и правил.
  Каждый набор тестов обнаружил восемь из девяти заранее зафиксированных дефектов. Девятый обнаружили все три агента с навыками,
  один агент с правилами и два агента без навыков и правил. Однако в `api-testing` соответствующую инструкцию добавили тем же коммитом,
  которым внесли дефект. Поэтому этот результат не доказывает пользу навыков. При проверке ещё десяти дефектов группа с навыками
  выявила дефект в 15 из 30 возможных случаев, а остальные группы — в 16 и 18 случаях соответственно. Ни один агент из группы с навыками не проверил два
  пункта контракта, выходивших за рамки тем этих навыков. В этой задаче наборы тестов у агентов с навыками оказались более похожими друг на друга,
  а работа заняла больше времени. Число обнаруженных дефектов не выросло. Теперь `api-testing` требует для каждого пункта контракта
  добавить тест или поставить пометку «не покрыто».

В лаборатории 28 намеренно внесённых дефектов, из них 19 в Shop и 9 в TodoMVC. При обязательной проверке в CI
команда `npm run test:workflow-controls` запускает опубликованные наборы тестов на исправных сборках (36 тестов) и при наличии 22 из этих дефектов.
Для каждого из 22 дефектов должно нарушиться именно то тестовое утверждение, которое предназначено для его обнаружения.

Для локального запуска проверок нужны Python 3.12+ и Node 24+.
Для сценариев с приложениями требуется Linux AMD64 или macOS arm64:

```bash
python3 -m pip install -r requirements-dev.txt
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 scripts/validate_skills.py
python3 scripts/build_index.py --check
python3 scripts/run_evals.py --static --all --min-pass-rate 90
npm ci
npm test
npm run test:qa
npx playwright install --with-deps chromium
npm run test:browser
npm run workflow:setup
npm run test:workflows
npm run test:mailpit
npm run test:workflow-controls
```

Команда `npm run test:workflows` и матрица контрольных прогонов охватывают опубликованные наборы из
`tests/workflows/generated/`. Наборы тестов из третьей серии и попытки из эксперимента «С навыками и без них» оцениваются отдельно
командами `node tests/workflows/run-matrix.mjs campaign3` и
`node tests/workflows/run-experiment.mjs <take>` соответственно. Инструмент семантической оценки
(`python3 scripts/judge_evals.py --static --all`) вызывает CLI `claude` и расходует токены,
поэтому в CI его не запускают.

Тесты примеров загружают функции прямо из блоков кода в Markdown, поэтому изменения в инструкциях тоже проходят проверку.
Браузерные сценарии используют контролируемые локальные фикстуры. В CI эти тесты запускаются отдельно от статической оценки.
Она проверяет охват материала по словам и выражениям, оставляя смысловые критерии для отдельной проверки.
Балл статической оценки не показывает долю задач, которые агент выполнил успешно.

Для применения навыков по-прежнему нужны реальные контракты приложения, данные, окружение и подтверждения результатов.
Успех на локальной фикстуре не подтверждает корректность работы в продакшене, соблюдение законодательства, приём данных последующими
системами или совместимость со всеми будущими версиями инструментов и моделей.
Отдельно отмечайте успешные, неудачные, повторные, пропущенные и заблокированные проверки, а также случаи с неизвестным результатом.
При обнаружении нового дефекта добавляйте сценарий, который его воспроизводит.
